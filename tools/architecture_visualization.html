Architecture Overview

PyqApp utilizes a Feature-First approach with Riverpod for state management and Supabase (dual-instance primary/secondary) and Hive (local caching) for databases.

Feature-First Structure

The code is structured around features (e.g., pyqs, subjects, auth) rather than technical layers. Each feature is self-contained, encapsulating its own UI, business logic, and data handling.

Inside a Feature Folder:

  • 📁 presentation/screens/
    Flutter screens representing pages/views.
  • 📁 presentation/providers/
    Riverpod StateNotifiers or Future/StreamProviders.
  • 📁 presentation/widgets/
    Highly reusable widgets specific to this feature.
  • 📁 data/repositories/
    Data fetching, caching, and mapping classes.
  • 📁 data/models/
    Data structure models (annotated with Hive annotations).

Cross-Cutting Support

Infrastructure components that provide unified services and utilities to all features across the application:

📁 services/

Integrations with external tools. E.g., push_notification_service.dart (Firebase), pdf_service.dart, and ai_service.dart.

📁 core/

Shared providers, local storage wrappers (like SharedPreferences initialization), and common network utilities.

📁 app/

App configuration, application shell initialization (app_initializer.dart), and routing definitions using GoRouter (router.dart).

Data & State Flow

How data flows from remote endpoints through Riverpod and renders in Flutter UI:

1. Remote Storage & API Supabase Primary (Syllabus/PYQs) & Secondary (Skulk/Login) act as sources of truth.
2. Cache & Repositories Repositories fetch remote data, save models into local Hive boxes, and serve offline-first data.
3. State Management (Riverpod) Providers watch repositories and expose states to UI elements automatically.
4. UI Rendering Flutter Screen Widgets (ConsumerWidgets) watch Riverpod providers to build the visual interfaces.
